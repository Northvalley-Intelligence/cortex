## Arm contract (both arms)
Input per pair: `(query, title)` ONLY. Output: an integer grade in `RELEVANCE_SCALE` (0–3) per pair (import the scale; never hardcode). Each arm writes predictions the harness can score, and reports its OWN per-pair latency so the harness aggregates median/p95 + peak RSS. Run each arm on all three eval sets: `cortex_validations.jsonl`, `wands_eval.jsonl`, and an ESCI eval sample (see below), producing `results/<arm>__<dataset>.json` via the harness.

Because ESCI-test is 181k rows, use a **fixed, seeded random sample** (e.g. 3,000 pairs, seed=42, stratified by grade) for the LLM-timed arms so this is tractable on one machine — record the sample size, seed, and that the SAME sample is reused for every arm (write it once to `data/esci_eval_sample.jsonl` so all arms and Cortex-live score identical pairs). WANDS is 233k rows — likewise sample 3,000 seeded/stratified to `data/wands_eval_sample.jsonl`. The Cortex-validation set (4,576) is small enough to use whole.

## Arm A — BM25 lexical baseline (`arms/bm25.mjs` or `.py`)
BM25 is a per-query *ranking* score, not a pointwise grade, so it needs calibration into 0–3:
1. Compute BM25(query, title). Build IDF over the **titles in ESCI-train** as the corpus; standard Okapi BM25 (k1≈1.5, b≈0.75). Tokenize lowercased alphanumerics; document the tokenizer.
2. **Calibrate 3 thresholds on ESCI-train** (NOT on any eval set) that map the BM25 score to a 0–3 grade by maximizing QWK against ESCI-train grades (grid or quantile search — document the method). Freeze thresholds, apply unchanged to every eval set.
3. This is expected to be a WEAK baseline (lexical overlap ≠ intent) — that is the point of including it. Report it honestly.

## Arm B — llama3.2:3b prompted via Ollama (`arms/ollama_prompt.mjs`)
Mirror Cortex's judging approach but purely local, for a fair "prompted-LLM" arm:
- Call Ollama (`http://127.0.0.1:11434/api/generate`), model `llama3.2:3b`, `temperature:0`, cap tokens ~120, `stream:false`.
- Build the prompt from Cortex's OWN frame + default rubric so it's comparable: read `JUDGE_FRAME_HEAD` / `DEFAULT_JUDGE_RUBRIC` structure from `src/relevance.mjs` conceptually (you may replicate the prompt-building by importing Cortex's exported helpers if available, e.g. `buildJudgeSystemPrompt`/`buildJudgePrompt`; if not exported, construct an equivalent prompt that uses `RELEVANCE_SCALE` — do NOT retype the label strings). Parse the one-line JSON `{"grade":n,...}`; on parse failure, record it as an error (do NOT coerce to 0), and report the parse-failure rate.
- Separate **cold** (first call, model load) from **warm** latency in the report.
- In the Arm-B result on `cortex_validations`, ADD a field `note: "reproduction — 92% of this set was generated by llama3.2:3b (see journal 03)"` so the circularity is never lost.
